1.1. Purpose
The Audience Module is the central data engine of the platform.
It is not simply a CRM.
It is the single source of truth for every customer, lead, subscriber, conversation participant, social follower, buyer, prospect, and business entity that interacts with the platform.
Every major module depends on it.
                   Audience Engine
                           │
      ┌────────────────────┼────────────────────┐
      │                    │                    │
   Broadcast             Inbox               CRM
      │                    │                    │
 Automation           Social Planner      Analytics
      │                    │                    │
      └────────────── AI Engine ────────────────┘
If this module is designed well, every future feature becomes easier.
If it is designed poorly, every future module accumulates technical debt.
________________


1.2. Core Principles
These principles are non-negotiable.
Principle 1 — One Person = One Contact
A human should exist only once inside a workspace.
Regardless of how they interact.
Example:

↓

↓

↓

________________


Principle 3 — Contacts Are Permanent
Deleting a contact should be extremely rare.
Instead, support lifecycle states such as:
* Active
* Archived
* Suppressed
* Merged
* Deleted (soft delete)
* Anonymized (for privacy compliance)
Hard deletion should be reserved for compliance workflows (e.g., GDPR/DPDP requests).
________________


Principle 4 — Lists Never Own Contacts
A Contact exists independently.
Lists only reference Contacts.
Contact


↓


List A


↓


List B


↓


List C
Deleting a List must never delete Contacts.
________________


Principle 5 — Segments Never Store Contacts
A Segment stores rules, not members.
Example:
Country = India


AND


Purchased > 2


AND


WhatsApp Opt-in = Yes
Members are computed from those rules.
________________


Principle 6 — Broadcasts Never Own Contacts
A Broadcast references an audience source:
* Contacts
* Lists
* Segments
* Tags
* Saved Filters
The audience remains independent of the campaign.
________________


Principle 7 — Audience Is Workspace Scoped
Every Contact belongs to exactly one Workspace.
No contact can cross workspace boundaries.
This aligns with your current multi-tenant model and RLS implementation.

1.8. Reachability
One of the biggest weaknesses in many CRM platforms is treating every contact as equally reachable.
Instead, React Commerce should distinguish:
* Exists
* Reachable
* Opted-in
* Deliverable
* Active
* Recently Active

* WhatsApp opted out
* Email invalid
* SMS unsubscribed
That contact should not appear as eligible for those campaign channels, even though it remains a valid CRM record.

1.10. Design Goals
The Audience module should achieve the following goals:
* Maintain exactly one canonical profile per person wherever possible.
* Scale efficiently on PostgreSQL/Supabase without requiring external search infrastructure.
* Support both simple users and enterprise workflows.
* Be fully compatible with your Broadcast, Inbox, CRM, and Automation modules.
* Be easy for AI coding agents to extend without major refactoring.
* Separate system-managed data, user-managed data, and derived/computed data cleanly.
* Keep every decision explainable and deterministic.

2.12 Contact Record Philosophy
Every field should answer one question:
"Will another module need this information?"
If yes, it belongs in the Contact model (or is derived from related data).
If no, it should remain outside the core object.
This keeps the Contact focused while still allowing it to evolve with Broadcasts, CRM, Inbox, Automations, Analytics, and future integrations.
________________


Design Note for React Commerce
One architectural change I recommend before we continue is introducing a distinction between:
* Core Contact Fields (columns in contacts)
* Computed Fields (derived from campaigns, conversations, orders, etc.)
* Custom Fields (user-defined)
* Integration Fields (Shopify, WooCommerce, Meta, future connectors)
Keeping these categories separate will make the platform significantly easier to maintain, optimize, and extend than storing everything as a single flat object or a large JSON blob.
Chapter 3 — Contact Identity Resolution & Deduplication Engine
________________


3.1 Purpose
The Identity Resolution Engine ensures that one real-world person corresponds to one Contact record inside a workspace.
It prevents:
* Duplicate broadcasts
* Duplicate conversations
* Incorrect analytics
* Split purchase history
* Broken automation flows
* AI hallucinating multiple customer profiles
Without this engine, the entire Audience module becomes unreliable.
________________

A Contact is not identified by one field.

11.40 Architectural Recommendation
Instead of separate engines, consolidate them into a Unified Query Platform.

│

├── Segment Engine
├── Query Compiler
├── Query Optimizer
├── Query Executor
├── Cache Manager
├── Result Counter
├── Explanation Engine
└── Analytics Collector
Why this matters
This is one of the biggest architectural opportunities in React Commerce.
Rather than treating Search, Filters, and Segments as three independent systems, they should be three different interfaces over the same underlying query infrastructure:
* Search answers: "Find this."
* Filters answer: "Show records matching these conditions."
* Segments answer: "Persist and reuse this query over time."
With this design:
* A saved filter can become a segment with one click.
* A segment can open in the filter builder for editing.
* AI can generate the same JSON query format regardless of entry point.
* Broadcasts, Analytics, CRM, and Automations all rely on a single, tested query engine.
This reduces duplicated code, ensures consistent behavior across the platform, and makes future capabilities—such as natural-language search or AI-generated reports—much easier to build.
